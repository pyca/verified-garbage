Fully verified retained-state scalar BlockMix
===========================================

Completion of the retained-state experiment recorded in CONTINUATION.txt.
The production x86-64 scrypt API now uses fused scalar BlockMix, SSE2 ROMix
memory loops, scalar MUL for table addressing, and direct V-table filling.
Twelve Salsa words stay in GPRs and four stay in scratch across input blocks.
The six callee-saved registers are saved/restored once per BlockMix call.
The standalone Salsa20/8 artifact retains its existing interface and proof.

Proof and integration
---------------------
FusedInit/Setup prove the initial load and scratch metadata setup.
FusedInvariant/Body reuse the established BlockMix output invariant and
prove the even/odd output layout while retaining all sixteen Salsa words.
FusedHalf/Tail prove pointer loading, core composition, pointer advancement,
countdown, and preservation of the scratch metadata and retained words.
FusedCorrect proves termination, final bytes, and register restoration.
FusedCT/Verified prove data-independent BlockMix traces and the public ABI
contract. ROMix and all SHA-256-backed scrypt variants use this artifact.
ROMix keeps its existing leakage contract for data-dependent table indices.
No TCB/ or Spec/ changes, unproved assumptions, new axioms, or heartbeat
limit increases were needed. Generated assembly comes only from Lean.

Validation
----------
- Targeted Lean builds: Artifacts.Scrypt.X86_64 and
  Generic.MdHash.X86_64.Scrypt, including the complete transitive proofs.
- Emitter: standard-axiom, compiler-override, and specification-origin audits;
  final re-emission is byte-identical to src/asm/x86_64/scrypt.rs.
- cargo test --release --test rfc7914: all 8 tests, including all 4 RFC vectors
  and the 1-GiB case, passed.
- cargo test --release --manifest-path bench/Cargo.toml --test scrypt:
  all 120 OpenSSL cases passed for each of default dispatch,
  VG_CPU_FEATURES=none, and VG_CPU_FEATURES=avx,avx2,bmi1,bmi2 (360 total).
- The fused copy-based control also passed all 120 OpenSSL cases.
- Lean import/speed rules, variant propagation, MCDT, architecture gates,
  vector provenance, generated algorithm tables, cargo fmt --check, and
  root cargo clippy --all-targets -- -D warnings passed.

Measurement method
------------------
AMD EPYC 9V74 (Zen 4), KVM, CPU 0 pinned, OpenSSL 3.5.7, Rust 1.99.0.
Five randomized/interleaved rounds (seed 7914), four preserved Cargo release
benchmark binaries; no compilation or other benchmarks overlapped timing.
Existing Criterion scrypt group: 10 samples, 0.3 s warmup, requested 1 s
measurement, r=8, p=1, password="password", salt="NaCl", 64-byte output.
Timings include allocation, both PBKDF2 calls, cleansing, and free.
These are native wall-clock measurements; no instruction-count claim is made.

Variants:
- baseline: original 1434e4dc0598e2e14a841d666239bf72d2e15fe0.
- direct: prior verified scalar scheduling/inlining/MUL + SSE2 + direct fill
  (production code at 1ce3ad2c and 247a5bdc).
- fused: this change, retaining Salsa state across BlockMix input blocks.
- fused-copy: this change using verified roMix instead of roMixDirect in
  the artifact, Scrypt.lean, and Whole/{Calls,Verified}.lean; same fused
  BlockMix, SSE2 loops, hash backends, compiler, and API. Its full proof and
  emitter audits passed. The production sources were restored before the
  final emitter check. The only algorithmic difference is table filling.

Raw run estimates: fused-api-runs.csv.
Original Criterion samples: fused-api-samples.csv.
Workspace drivers/logs/binaries: /workspace/scratch/salsa-continuation/;
bench-fused.py runs the comparisons; summarize-fused.py writes raw CSVs and
computes medians and paired bootstrap intervals. Original JSON is under
fused-measurements/. Binaries are verified-{baseline,direct,fused,fused-copy}-bench.

Full public API results
-----------------------
Medians of five run means, milliseconds:

Variant                 N=1024   N=16384
Original baseline        2.160    37.060
Previous verified        1.879    30.855
Fused + direct fill      1.637    28.575
Fused + copy filling     1.660    29.345
OpenSSL, fused runs      2.248    37.013

Matched by shuffled round, median latency reductions and descriptive 95%
percentile bootstrap intervals (10,000 resamples, seed 7914, five pairs):

Comparison                  N=1024                  N=16384
Original -> fused           24.65% [21.02,25.20]      22.69% [19.58,30.41]
Previous -> fused            9.53% [ 4.71,26.24]       7.57% [ 2.71,14.27]
Fused copy -> fused direct    2.57% [-7.10, 4.10]       2.62% [ 0.27, 3.81]

Fused/OpenSSL within-run latency ratios have medians 0.750 and 0.763,
respectively: about 25% and 24% lower latency on this host.
The previous and fused variants' N=16384 OpenSSL controls were 36.975 and
37.013 ms, respectively, supporting the incremental fusion result.

Retain the existing direct-fill path. It was faster than the fused copy
control in all five N=16384 pairs, but the difference is modest: the copy
variant's OpenSSL control was also slower (38.337 ms). Do not attribute the
entire 2.62% to direct filling independent of VM noise. N=1024 does not
establish a separate direct-fill advantage. The clear result is the fused
architecture's gain over both the previous verified code and OpenSSL.
These measurements are specific to this Zen 4 VM and sequential workload;
they do not establish universal x86-64 or concurrent-hashing performance.
