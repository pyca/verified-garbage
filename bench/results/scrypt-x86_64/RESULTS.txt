Verified scalar Salsa/BlockMix and ROMix optimization
====================================================

Historical scalar-scheduling experiment. Subsequent SIMD memory loops,
direct table filling, and fully verified retained-state fusion are described
in CONTINUATION.txt and FUSED.txt.

Baseline: 1434e4dc0598e2e14a841d666239bf72d2e15fe0
Scheduling + inlining: 84a8a7ca
Scheduling + inlining + address multiply: 0ff1ac70
A scheduling-only control used the reordered Salsa implementation/proof with
baseline BlockMix and ROMix. No handwritten replacement assembly was used:
the Rust benchmarks use Lean-emitted code throughout.

Retained changes
----------------
* Interleave the four independent scalar quarter-round chains at each rotation.
  Prove equality to the RFC's sequential double round by vector extensionality.
* Inline the proved Salsa body into BlockMix. Prove functional composition with
  WP.inline and constant-time composition with RelCT; update enclosing stack
  frame proofs for the smaller call depth. Public contracts retain their bounds.
* Replace ROMix's bit-at-a-time address multiplication with four instructions:
  save the base in rdi, unsigned MUL, restore the base to rdx, add the low product.
  Prove modular multiplication and register preservation, and compose into ROMix.

Salsa arithmetic is scalar and uses the baseline x86-64 ISA. The existing
four spilled words and per-core save/restore remain. This is not the C
prototype's full state-retention optimization. Direct V-table fill and SIMD
memory loops are not ported here. No Spec/ or TCB/ changes, new axioms, proof
escape hatches, or heartbeat-limit increases were needed.

Machine and method
------------------
AMD EPYC 9V74 (Zen 4), KVM guest, benchmark pinned to logical CPU 0, one thread.
Rust 1.99.0 (b940084d7 2026-09-28), normal Cargo bench release profile.
OpenSSL 3.5.7; GCC 14.2.0 for the diagnostic C driver.
CPU dispatch left at its detected default for timings. Hash backend tests also
force VG_CPU_FEATURES=none and VG_CPU_FEATURES=avx,avx2,bmi1,bmi2.

All full-API benchmarks use password="password", salt="NaCl", r=8, p=1,
64-byte output, and include allocation, both PBKDF2 calls, and normal cleansing.
Five shuffled rounds of four preserved binaries; shuffle seed 7914. Each binary
runs the existing Criterion scrypt group (10 samples, 0.3 s warmup, requested
1 s measurement; Criterion extends sampling where needed). No concurrent builds
ran during these measurements. The guest exhibits substantial timing variation.

Full API: median of five run means, milliseconds
----------------------------------------------
N        baseline   schedule   + inline   + MUL (final)   final reduction
1024       2.182      1.964      2.022       1.953              10.5%
16384     38.491     33.842     34.810      34.021              11.6%

OpenSSL's median across all 20 interleaved control runs was 2.276 ms and
38.650 ms respectively. Final vs OpenSSL within-run latency ratios have
medians 0.862 and 0.868. These observations establish a win on this host,
not a claim about every x86-64 CPU or concurrent password hashing.

Baseline run-mean ranges: 2.107–2.368 ms; 36.806–42.430 ms.
Final run-mean ranges:    1.860–2.081 ms; 33.282–36.903 ms.
The full-API differences between intermediate stages are noisy: scheduling
alone has a lower raw median than final at N=16384. Do not infer individual
incremental gains by subtracting these aggregate medians.

All four emitted implementations are linked in one process, using identical
input, reused memory, and shuffled order (seed 7914). One warmup round; 20,
3, and 1 operations per timed sample for the three costs. The input is reset
before each operation and every result is compared with the baseline output.
These timings exclude PBKDF2, allocation, and cleanup; they explain mechanisms,
not full-API latency. Assembly extraction only substitutes symbol names.

Paired median ROMix time reductions, with percentile bootstrap 95% intervals
(5000 resamples, seed 7914, paired by round):
N        baseline -> schedule    schedule -> inline    inline -> MUL
1024      9.09% [8.71,10.04]       2.17% [-0.02,2.55]     1.54% [0.14,2.61]
16384     9.26% [8.70,10.86]       0.08% [-0.60,0.68]     2.40% [1.19,3.36]
65536     8.57% [7.75, 9.21]       1.22% [ 0.72,2.48]     3.33% [1.86,4.41]

Inlining alone is inconclusive at the two smaller costs. It is retained for
the larger-cost gain, removal of calls, and simpler integration of the core.
Most of the combined improvement comes from scheduling and multiplication.

Heap allocation and scratch sizes are unchanged. No instruction-count or
hardware-counter improvement is claimed. In the release binary, nm reports
BlockMix growing from 384 to 3840 bytes; the old separately linked 1792-byte
Salsa body is no longer retained, giving a net 1664-byte increase for these
symbols. This is the tradeoff for inlining two fully unrolled cores.

Validation
----------
* Targeted Lean builds: Artifacts.Scrypt.X86_64 and Generic.MdHash.X86_64.Scrypt.
  Functional, ABI/memory, and constant-time proofs succeed. ROMix retains the
  existing contract's explicitly public data-dependent table indices.
* Emitter audits: standard axioms only, no compiler overrides, Spec origin.
  Re-emission matches src/asm/x86_64/scrypt.rs byte for byte.
* Eight RFC 7914 tests pass with normal and baseline CPU dispatch, including
  the 1 GiB vector, parameter/error checks, variable lengths, and verification.
* 120 full-API differential cases against OpenSSL pass in each of the normal,
  baseline, and AVX2 hash-backend configurations: N=2,16,1024; r=1,2,3,8,17;
  p=1,2; output lengths 1,33,64,100, with binary passwords and salts.
* Rust formatting and root all-target Clippy; benchmark test Clippy.
* Lean import/speed rules, architecture gates, vector provenance, variant
  propagation, MCDT checks; algorithm-table regeneration produces no change.
* The entire multi-architecture Lean build/emitter and full unrelated Rust
  test suite have not been run. These are still required before pushing.

Reproduction
------------
From lean/:
  lake build +VerifiedGarbage.Artifacts.Scrypt.X86_64 \
    +VerifiedGarbage.Generic.MdHash.X86_64.Scrypt

From the repository root:
  cargo test --features cpu-features-env --test rfc7914
  VG_CPU_FEATURES=none cargo test --features cpu-features-env --test rfc7914
  cargo test --manifest-path bench/Cargo.toml --test scrypt
  VG_CPU_FEATURES=none cargo test --manifest-path bench/Cargo.toml --test scrypt
  VG_CPU_FEATURES=avx,avx2,bmi1,bmi2 cargo test --manifest-path bench/Cargo.toml --test scrypt
  cargo bench --manifest-path bench/Cargo.toml --bench primitives --no-run
  taskset -c 0 <preserved-benchmark-binary> --bench '^scrypt/' \
    --warm-up-time 0.3 --measurement-time 1 --noplot

Build and preserve a binary at each revision; shuffle their execution order.
api-samples.csv contains the original Criterion iteration counts and elapsed
nanoseconds; api-runs.csv contains the run estimates and intervals.
romix-runs.csv contains every diagnostic ROMix sample.

The workspace also retains the drivers, emitter audit logs and preserved
binaries under /workspace/scratch/salsa-experiment:
  EmitScrypt.lean (ordinary trusted emitter plus its audits, limited to the
    complete scrypt/SHA-256/HMAC/PBKDF2 dependency set)
  bench-verified.py (full-API interleaving)
  bench-generated.py, bench-generated.c (diagnostic generated-code comparison)
  final-build.log, final-emit.log
